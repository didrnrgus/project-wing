## 1. 프로젝트 소개

ProjectWing은 위아래 벽 사이로 끝없이 이어지는 통로를 날며 벽과 장애물을 피하고, 비행 거리로 순위를 겨루는 게임입니다. 상용 엔진을 쓰지 않고 **윈도우 생성, 렌더링, 입력, 충돌, UI, 에셋 관리를 직접 구현한 C++/DirectX 11 프레임워크** 위에서 동작합니다.

- **조작은 단순하게, 규칙은 깊게** 만들었습니다. 마우스 왼쪽 버튼을 누르면 오르고 떼면 내려가며, 스페이스바로 부스트를 켜면 속도와 거리 증가량이 2배가 됩니다. HP는 시간이 지나면서 줄고 충돌하면 크게 깎이며, 오래 버틸수록 통로가 좁아집니다.
- **5종의 캐릭터, 4종의 아이템, 3개의 맵** 조합으로 스탯(HP, 속도, 민첩, 방어, 기절 시간)이 달라집니다.
- **싱글플레이**는 서버 없이 클라이언트가 모든 규칙을 계산하고, 기록을 Notion 데이터베이스 랭킹에 등록합니다.
- **멀티플레이**는 방장 클라이언트가 소켓 서버를 자식 프로세스로 띄우고, 최대 5명이 TCP로 접속해 같은 장애물을 보며 경쟁합니다. 거리, HP, 장애물은 서버가 계산합니다.
- **게임 수치는 코드가 아니라 GitHub Pages의 JSON**에 있어서, 맵 모양이나 밸런스를 바꿀 때 다시 빌드할 필요가 없습니다.

## 2. 플레이 영상

### 싱글플레이 (1280×720, 1분 42초)

닉네임 변경 → 랭킹 화면 → 로비에서 캐릭터, 아이템, 맵 선택 → 인게임 → 사망 → 결과 화면 순서입니다. 인게임에서는 30초 동안 벽과 장애물에 한 번도 부딪히지 않고 부스트를 섞어 비행한 뒤, 일부러 장애물에 부딪혀 충돌 → 스턴 → 보호 → HP 0 → 사망까지의 흐름을 보여 줍니다.

▶ 영상 파일: [videos/singleplay.mp4](videos/singleplay.mp4)

### 로컬 멀티플레이 (1920×1080, 1분 41초)

한 PC에서 게임 클라이언트 4개와 소켓 서버를 실행해 녹화했습니다. 왼쪽 큰 화면은 방장 화면(원본 1280×720)이고, 오른쪽은 참가자 Diane, Jethro, Yang의 화면입니다. 플레이 숙련도가 상(Kkuk) · 중(Diane) · 중(Jethro) · 하(Yang)인 4명이 함께 플레이하는 상황입니다. 방장이 서버를 띄우고 참가자가 접속하는 장면, 로비에서 방장이 닉네임을 바꾸면 모든 참가자 화면에 반영되는 장면, 전원 Ready 후 시작, 같은 장애물이 모든 화면에 나타나는 인게임 동기화, 숙련도 순서대로 탈락한 뒤의 결과 순위(415m · 281m · 273m · 245m)까지 담았습니다.

▶ 영상 파일: [videos/multiplay_local4.mp4](videos/multiplay_local4.mp4)

### 프레임 루프와 씬 흐름

![프레임 루프와 씬 흐름](images/diagram_02_loop_scene.jpg)

- 메인 루프는 `PeekMessage`로 윈도우 메시지가 없을 때마다 `Timer → Input → Update → Collision → Render → Sound`를 한 번 실행합니다.
- 씬 전환은 작업 스레드에서 로딩 문구를 띄운 뒤 플래그만 세우고, 실제 교체는 메인 스레드의 다음 Update에서 합니다. 새 씬은 교체 전에 초기화를 끝내 두므로 빈 화면이 보이지 않습니다.

### 인게임 객체 연결

![인게임 객체 연결](images/diagram_04_ingame_objects.jpg)

- 객체끼리 구체 클래스를 참조하지 않고 역할 인터페이스(`IPlayerStatController`, `IGamePlayStateController`, `IGamePlayShakeController`, `IObjectNetworkController`)로만 통신합니다.
- 벽과 장애물은 스스로 속도를 갖지 않고 매 프레임 내 플레이어의 `Speed × Boost`만큼 왼쪽으로 움직입니다. 플레이어는 화면 가로 위치에 고정되어 있고, 스턴이면 맵 전체가 멈춥니다.

## 5. 주요 기능

### 5.1 자체 C++/DirectX 11 엔진

| 영역 | 구현 내용 |
| --- | --- |
| 오브젝트 · 컴포넌트 | `CObject`(참조 카운트) → `CSceneObject`가 루트 `CSceneComponent` 아래 컴포넌트 트리를 가집니다. 스프라이트, 카메라, 위젯, 오디오, 콜라이더가 모두 씬 컴포넌트이며, 부모를 옮기면 자식이 회전까지 반영해 따라갑니다. 수명은 `CSharedPtr<T>`로 관리합니다 |
| 씬 수명주기 | `Init`에서 Input, Camera, Collision, Asset, UI 매니저를 만든 뒤 `InitAsset → InitObject → InitWidget` 순으로 호출합니다. 매 프레임 `Input → PreUpdate → Update → PostUpdate → Collision → Render` 순으로 돌고, 비활성 객체는 PostUpdate에서 정리합니다 |
| 렌더링 | 레이어별 렌더 목록을 정렬해 그리고, 블렌드와 깊이 상태는 이름으로 관리합니다. 셰이더는 실행 시 `.fx`를 컴파일하며 상수 버퍼를 용도별 클래스(Transform, Sprite, UI, Animation2D, Collider 등)로 나눴습니다 |
| 텍스트 · UI | Direct3D 백버퍼를 Direct2D 렌더 타깃으로 연결해 DirectWrite로 한글 텍스트를 그립니다. 위젯은 버튼(상태별 텍스처, Hover/Click 콜백), 이미지, 텍스트, 프로그레스 바, 컨테이너로 구성되고 ZOrder로 렌더와 마우스 충돌 순서를 정합니다 |
| 입력 | DirectInput으로 키보드와 마우스를 읽고, `AddBindKey` + `AddBindFunction(Down/Hold/Up)`으로 이름 기반 키 바인딩을 제공합니다. Ctrl, Alt, Shift 조합도 지원합니다 |
| 애니메이션 | Unity 스프라이트 에디터에서 뽑은 스프라이트시트 JSON을 읽어 프레임 애니메이션을 재생합니다. 캐릭터 5종은 같은 시퀀스를 쓰고 데이터의 색과 크기만 바꿉니다 |

### 5.2 충돌 시스템

- **콜라이더 4종**: AABB, OBB, 원, 선분. 벽은 선분, 장애물은 회전하는 OBB(크기의 70%), 플레이어는 원(스프라이트 높이 × 0.2)입니다.
- **쿼드트리 분할**: 노드에 콜라이더가 5개를 넘으면 나누고(최대 깊이 4), 같은 노드 안에서만 쌍을 검사합니다.
- **충돌 프로파일**: 채널별 충돌 여부를 매트릭스로 정합니다. 내 플레이어와 맵(벽, 장애물) 사이에서만 충돌하고, 다른 플레이어끼리는 통과합니다.
- **콜백**: `SetCollisionBeginFunc(this, &T::Func)`로 충돌 시작과 끝을 받습니다. 마우스와 UI의 충돌도 같은 단계에서 처리합니다.

### 5.3 라인 노드 기반 맵 생성과 스크롤

- 맵 데이터는 300px 구간마다 위/아래 벽 높이를 적은 노드 목록입니다. 노드 i와 i+1을 잇는 선분이 벽 스프라이트와 충돌 선분이 됩니다.
- 화면에는 7개 구간만 두고, 왼쪽으로 빠진 구간을 지워 오른쪽 끝에 새 구간을 붙여 재사용합니다.
- 노드 목록을 한 바퀴 돌 때마다 위쪽 벽은 `difficulty_rate`만큼 내려오고 아래쪽 벽은 올라와, **오래 버틸수록 통로가 좁아집니다**.
- 같은 객체를 타이틀 배경 데모에도 쓰며, 이때는 통로가 좁아지지 않게 했습니다.

### 5.4 플레이어 규칙 (스탯, 충돌, 사망)

| 규칙 | 공식 · 동작 |
| --- | --- |
| 최종 스탯 | 캐릭터 기본값 + 장착 아이템 보너스 합 |
| 거리 | `Speed × dt × 0.01 × 부스트배율` m (100px = 1m, 부스트 2배) |
| 자연 HP 감소 | 초당 `1 × (1 − Def/100)` |
| 충돌 데미지 | `max(0, 맵 충돌 데미지 − Def)` |
| 충돌 후 상태 | 데미지 → 스턴(캐릭터별 시간, 맵 정지 + 카메라 흔들림) → 보호(2초 무적, 반투명) |
| 사망 | 싱글: HP 0이면 조작이 막힌 채 떨어지다가 다음 충돌에서 사망 / 멀티: 서버가 판정 |

플레이 상태(`Ready → ReadyCount → Start → Freze → Dead`)는 씬이 한 번만 바꾸면 플레이어, 벽, 장애물, HUD에 모두 전파됩니다. 카운트다운 중 입력 차단과 HP 0 이후 조작 금지가 이 상태 하나로 처리됩니다.

### 5.5 장애물 오브젝트 풀

- 장애물 10개를 미리 만들어 두고 재사용합니다. 오른쪽 끝에서 활성화되어 왼쪽 끝을 넘으면 비활성화됩니다.
- 싱글에서는 맵의 `obstacle_interval_time`마다 크기, 회전, 높이를 무작위로 정하고, 멀티에서는 서버가 정한 값(`MSG_OBSTACLE`)으로 생성해 **모든 참가자가 같은 장애물을 봅니다**.

### 5.6 데이터 드리븐 설계 (GitHub Pages JSON)

- 시작할 때 `config`, 맵 3개, 캐릭터, 아이템, 스탯 종류, 색상 JSON을 순서대로 받아 `CDataStorageManager`에 저장합니다. 단계마다 로딩 문구를 보여 줍니다.
- 속도, HP, 데미지, 맵 모양, 장애물 주기, 색상, 랭킹 보관 수를 **JSON만 고쳐서 바꿀 수 있고 클라이언트와 서버를 다시 빌드할 필요가 없습니다**. 서버도 같은 JSON을 받아 계산하므로 규칙이 어긋나지 않습니다.

### 5.7 멀티플레이 클라이언트

- **TCP 패킷**: 12바이트 헤더(`senderId`, `msgType`, `bodyLen`, pack 1) + 가변 바디. 메시지 종류는 클라이언트→서버 14종, 서버→클라이언트 27종입니다.
- **스레드 분리**: 수신 스레드가 헤더와 바디를 정확히 읽어 뮤텍스로 보호한 큐에 넣고, 하트비트 스레드가 1초마다 생존 신호를 보냅니다. 게임 로직은 메인 스레드에서만 실행됩니다.
- **리스너 패턴**: 씬이 매 프레임 큐를 비우며 메시지를 등록된 리스너(플레이어, 장애물, 위젯)에게 분배하고, 각 리스너가 `msgType`과 `senderId`로 걸러 처리합니다. 오브젝트는 생성 시 `AddListener`, 소멸 시 `RemoveListener`를 호출합니다.
- **서버 권한과 클라이언트 반응성의 분리**: 내 캐릭터의 높이는 클라이언트가 바로 움직이고 서버에는 버튼 상태만 보냅니다. 반면 거리와 HP는 서버 값을 기준으로 덮어씁니다. 충돌 판정은 클라이언트가 하고, 데미지 적용과 스턴, 사망은 서버가 결정합니다.
- **방장 서버 실행**: 방장이 "멀티 플레이"를 누르면 서버 exe를 자식 프로세스로 띄우고 Job Object(`KILL_ON_JOB_CLOSE`)에 묶어, 방장 게임이 꺼지면 서버도 함께 종료되게 했습니다.

### 5.8 소켓 서버

- `select()` 기반 **단일 스레드** 루프입니다. 한 루프에서 접속 수락 → 수신과 메시지 처리 → 50ms 게임 틱 → 끊을 클라이언트 정리 → 송신 버퍼 flush를 차례로 처리하므로 공유 상태에 락이 없습니다.
- 클라이언트별 수신/송신 버퍼를 두어 헤더와 바디가 다 모였을 때만 처리하고, 바디 길이가 범위를 벗어나면 연결을 끊습니다.
- 방 상태는 `Lobby → Countdown → Playing → Lobby`입니다. 50ms마다 살아 있는 플레이어의 거리, 높이, HP를 계산해 전원에게 보내고, 장애물을 생성하고, 전원이 사망하면 게임을 끝낸 뒤 로비 상태를 초기화합니다.
- 방이 가득 찼거나 게임 중이면 거절 사유를 보내고 송신만 닫은 뒤 클라이언트가 끊기를 기다립니다. 바로 소켓을 닫으면 RST가 나가 거절 메시지가 유실될 수 있기 때문입니다.
- 10초 동안 아무 메시지가 없으면 연결을 끊고, 방장이 나가면 가장 먼저 들어온 사람에게 방장 권한을 넘깁니다.

### 5.9 Notion API 랭킹

- libcurl로 Notion REST API를 호출해 기록을 조회, 등록, 삭제(보관)합니다.
- 기록은 **맵별**, **캐릭터별** 두 카테고리로 순위를 매기고, 카테고리 값마다 보관할 최대 개수를 설정 JSON으로 정합니다.
- 등록 알고리즘: 사망 후 두 카테고리의 기존 기록 수를 확인하고, 꽉 찼으면 꼴찌보다 멀리 갔을 때만 꼴찌를 지우고 등록합니다. 둘 중 하나라도 순위권이면 등록하고 랭킹을 다시 조회한 뒤 결과 화면에 "신기록"을 표시합니다.
- HTTP 요청은 모두 작업 스레드에서 실행해 화면이 멈추지 않게 했습니다.

### 5.10 화면 흐름과 UI

- 씬은 타이틀, 로비, 인게임, 결과, 랭킹 5개이며, 씬마다 화면 위젯 하나가 UI를 맡습니다. 공통 부모 `CSceneWidget`이 로딩 오버레이와 안내 문구 큐, 씬 전환을 제공합니다.
- 로비는 싱글/멀티에 따라 오른쪽 패널을 바꿉니다(간이 랭킹 ↔ 참가자 목록). 아이템 목록 펼치기, 툴팁, 스탯 보너스 표시, 맵 난이도 아이콘 애니메이션을 구현했습니다.
- 인게임 HUD는 카운트다운, HP 게이지, 거리, 장착 아이템, 다른 참가자 정보를 보여 줍니다.
- Win32 메뉴 바로 닉네임, 방장 IP("다른 방에 참가하기"를 켜면 나타남), 언어를 설정하고, 창 제목에 현재 닉네임과 IP를 표시합니다.

### 5.11 영어 / 한국어 로컬라이징

- 화면 문구를 키(`ELocKey`)별 `{영어, 한국어}` 테이블로 관리하고 `LOC(Key)` 매크로로 가져옵니다. 테이블에 키를 빠뜨리면 `static_assert`로 **컴파일 단계에서 실패**하게 해 누락을 막았습니다.
- 언어는 exe 폴더의 `Language.ini` → 없으면 OS UI 언어 순으로 정하고, 메뉴에서 바꾸면 메뉴 바와 창 제목은 즉시, 게임 UI는 다음 화면 전환부터 반영됩니다.
- 폰트는 Noto Sans KR을 써서 두 언어를 모두 렌더링합니다.

### 5.12 GitHub Actions 자동 릴리즈

- `main`에 push하면 버전 태그(`X.Y.Z`)를 계산하고, Release x64로 클라이언트와 서버를 빌드한 뒤, 실행에 필요한 파일(exe, DLL, VC++ 런타임, 에셋, 셰이더, 서버)을 묶은 zip을 GitHub Release에 올립니다.
- 기본은 patch +1이고, 커밋 제목에 `#minor`/`#major`를 넣으면 해당 자리를 올립니다. 빌드가 성공해야 태그가 생깁니다.
- 에셋과 라이브러리는 Git LFS로 관리하고, 워크플로에서 LFS 객체를 캐시해 대역폭을 아낍니다. 문서만 바뀐 push에서는 실행되지 않습니다.

## 6. 문제 해결 사례

### 6.1 벽 충돌 판정이 벽 스프라이트 주변에서 흔들리던 문제

- **증상**: 벽에 닿지 않았는데 부딪히거나, 닿았는데 통과하는 경우가 있었습니다. 디버그 빌드에서 콜라이더 외곽선을 그려 보니 충돌 선분이 벽 스프라이트 주변에서 흔들리고 있었습니다.
- **원인**: 스크롤할 때 부모 스프라이트를 옮긴 뒤 자식 콜라이더도 한 번 더 옮기는 이중 이동이 있었고, 엔진의 `SetWorldPos`가 자식 위치를 갱신할 때 부모 회전을 반영하지 않아 오차가 매 프레임 누적됐습니다.
- **해결**: 위치 전파 규칙을 `월드 위치 = 상대 위치 × 부모 월드 회전 + 부모 월드 위치`로 통일했습니다. `SetWorldPos`는 부모의 역회전으로 상대 위치를 구하고, 회전 변경과 `AddChild`도 같은 규칙으로 자식과 손자까지 재귀로 다시 배치하게 고쳤습니다. 이중 이동을 제거하자 콜라이더가 스프라이트와 정확히 겹쳤습니다.

### 6.2 유실된 서버 소스를 프로토콜 분석으로 다시 작성

- **상황**: 멀티플레이 서버의 원본 소스가 유실되어 실행 파일만 남아 있었습니다.
- **접근**: 클라이언트 코드가 주고받는 메시지 타입과 바디 레이아웃을 전부 정리해 프로토콜 문서를 만들고, 원본 exe의 문자열(거절 사유, 로그 문구, 데이터 URL)과 실제 실행 측정(카운트다운 시간, 동기화 주기)으로 동작을 확인한 뒤 서버를 새로 작성했습니다.
- **개선**: 원본에서 문제가 되던 동작은 일부러 바꿨습니다. 예를 들어 원본은 게임 중 접속을 거절하지 않아 늦게 들어온 사람에게 카운트다운이 오지 않았는데, 새 서버는 `"Game is in progress."`로 거절합니다. 동기화 주기는 원본 약 180Hz에서 20Hz(50ms 틱)로 낮췄습니다.
- **검증**: Python 테스트 클라이언트 2~3개를 서버에 직접 붙여 34개 항목(접속 순서, 81바이트 방 정보, 로비 중계, 시작 거절/승인, 게임 중 접속 거절, 동기화, 스턴 중 데미지 무시, 사망, 게임 오버 후 재시작, 방장 위임 등)을 확인했고, 한 PC에서 클라이언트 4개로 접속부터 결과 화면까지 실행해 확인했습니다(위 멀티플레이 영상).

### 6.3 방 정보 패킷 정렬 문제 예방

- 방 정보 메시지는 플레이어 레코드(`int`, `bool`, `int`, `int[3]`, `char[64]`)를 패딩 없이 이어 붙인 81바이트 구조입니다. 서버가 `bool`을 4바이트로 보내거나 닉네임을 64바이트로 채우지 않으면 두 번째 플레이어부터 값이 어긋납니다.
- 헤더와 레코드를 `#pragma pack(1)`로 고정하고, 레이아웃을 문서에 바이트 단위로 적어 서버와 클라이언트가 같은 기준을 쓰게 했습니다. enum은 양쪽에서 항상 끝에만 추가하도록 규칙을 정했습니다.

### 6.4 CI 빌드 환경과 버전 규칙

- `windows-latest` 러너가 VS 2026으로 바뀌면서 v143 툴셋이 빠져 빌드가 실패하는 것을 확인하고, 러너를 `windows-2022`로 고정했습니다.
- 커밋 본문에서 버전 키워드를 설명하다가 major 버전이 잘못 올라간 일이 있어, 키워드를 커밋 제목에서만 찾도록 바꿨습니다.

## 7. 알려진 한계와 개선 계획

코드를 전수 분석해 문제를 문서로 정리해 두었고, 우선순위가 높은 것은 다음과 같습니다.

| 항목 | 현재 상태 | 개선 방향 |
| --- | --- | --- |
| 랭킹 API 키 | 클라이언트가 설정 JSON에서 Notion 키를 받아 직접 호출 | 랭킹 등록을 중간 서버나 서버리스 함수로 대리해 키를 클라이언트에서 제거 |
| 높이 동기화 | 내 화면의 내 높이(클라이언트)와 남이 보는 내 높이(서버)를 서로 보정하지 않음 | 주기적으로 서버 높이와 비교해 보간 보정 |
| 연결 해제 | 로비에서 타이틀로 돌아가도 소켓과 멀티 상태가 남음 | 화면 이탈 시 명시적으로 연결 종료, 종료 순서(소켓 닫기 → 스레드 join) 정리 |
| 랭킹 조회 | Notion 쿼리 페이지네이션 없음(최대 100개) | 커서 기반 페이지네이션 적용 |
| 한 PC 다중 실행 | DirectInput을 백그라운드 모드로 읽어 한 창의 입력이 다른 창에도 들어감 | 포커스가 있는 창에서만 입력 처리 |
